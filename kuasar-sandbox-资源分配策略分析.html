一、项目定位：不是「容器运行时」，是高密度 MicroVM 沙箱平台

kuasar-sandbox 是华为 2026 年开源的 高密度 MicroVM 沙箱平台，面向 AI Agent / Serverless / Code Interpreter / RL 负载（topics 含 ai-agente2bkvmmicrovmsnapshot）。它与 2023 年华为云开源的经典容器运行时 kuasar-io/kuasar 是两个不同项目——前者是「E2B 兼容的独立 guest 内核沙箱」，后者是「多沙箱容器运行时（containerd Sandbox API）」。

本仓库是「系统级设计 + 聚合发布」的 canonical 仓库，实现拆在 5 个组件仓库：

组件资源相关职责关键二进制 / 包
sandboxer单沙箱资源执行：cgroup、virtio-balloon、VMM 生命周期、on-demand 内存加载sandbox-ctl、sandbox-init、补丁版 cloud-hypervisor；pkg/resctl/pkg/resource/pkg/config
orchestrator节点资源准入 + 集群放置：Reservation Controller、共享池、水位线、placenode-ctl、cluster-ctl；internal/nodectl
accelerator镜像/快照数据访问、稀疏存储、按需加载cache-ctl/store-ctl 等（存储面，不涉及 CPU 分配）
connectoreBPF/TC 网络、TAP 交接（数据面，不涉及 CPU 分配）connector-ctl
guest-runtimeguest 内核 + 运行时镜像vmlinux + sandbox-runtime.bundle

设计原则明确「Separate control and execution」：orchestrator 只管准入和共享池，sandboxer 才执行单个沙箱的 cgroup/balloon/VMM 操作——节点控制器不直接改沙箱 cgroup、不调 balloon。

二、资源治理总架构：一个「内存多路复用」闭环

kuasar-sandbox 的资源模型不是「每个沙箱硬占一份 CPU/内存」，而是面向「Agent 负载长时间等待、短时突发」的高密度模型。内存控制拆成两个独立流和三个角色：

角色机制作用
Balloon / Budgetvirtio-balloon 膨胀/收缩「让 idle 沙箱交回 guest 内存」的执行器；deflate 才释放 Budget
NodeReservation节点级分配账本跨沙箱复用的记账；只有本地 shrink 落账为更小的 reservation，内存才可被他人复用
memory.highcgroup v2 宿主节流宿主侧节流边界 + 压力反馈，不是硬上限、不是回收所有者
源码结论：增长「先向节点申请 Grant → 抬 memory.high → balloon deflate」；收缩「先 balloon inflate → 观察安全 → 降 memory.high → 释放 Reservation」。增长优先保安全、收缩保守滞后。Capacity 是单沙箱上限，NodeReservation 是节点当前承诺量，二者刻意分离——这是超卖（oversubscription）的核心。

三、逐维度结论（源码证据驱动）

3.1 CPU：不绑核，只做 cpu.weight 相对权重

kuasar-sandbox 对 CPU 的策略是三不：不绑核、不硬配额、不做 NUMA 亲和。CPU 只有两个量：

配置字段语义实现
resources.capacity.cpuguest 看到的 vCPU 数（决定 vCPU 拓扑）传给 Cloud Hypervisor 的 boot/max vcpus
resources.allocatable.cpu「可分配的相对调度规格」映射为 cgroup v2 cpu.weight（相对权重）
sandbox.md（原文）：「Capacity CPU determines vCPU topology. In cgroup mode, allocatable CPU maps to cpu.weight; without a cgroup it must equal capacity CPU, so a separate fractional allocation cannot be expressed.」
node-resource.md §7.2（原文）：「cpuAllocatable: the relative scheduling specification mapped to cpu.weight, without a hard fractional-core quota or unconditional performance guarantee.」

关键含义：

  • 无 cpuset.cpus 绑定、无 cpu.max 硬配额（上限为 max）、无 exclusive cpu partition。
  • Cloud Hypervisor v52 虽支持 --cpus affinity=[vcpu@[host_cpus]]（逐 vCPU 绑核），但 sandboxer 的配置 schema 里没有暴露任何 affinity 字段，全文 grep 无 affinity/cpuset/topology 绑定项。
  • 多个沙箱的 vCPU 线程由宿主 CFS 调度，可自由漂移并互相重叠，隔离效果仅来自 cpu.weight 的相对权重。

3.2 内存页型：小页 + THP，非静态大页；用 balloon 回收

内存按「固定上限 + 气球回收 + 宿主节流」三层管理，配置结构：

resources:
  capacity:   { cpu: 2, memory: 2GiB }   # capacity.memory = 固定 VM 上限（Capacity）
  allocatable: { memory: 256MiB }        # 默认 headroom，balloon 收缩目标（不是 Budget、不是 free）
  startup:    { memory: 2GiB }           # 首个可信冷启动报告前的 headroom
  overhead:   { memory: 32MiB }          # 宿主 VMM 开销（节点记账用）
  watermark_high: { ratio: 0.875 }       # memory.high 水位比例
  • 大页：schema 全文无 hugepages 字段；Cloud Hypervisor 的 --memory hugepages=on 能力未被启用。内存凭 mmap + 宿主 THP（madvise MADV_HUGEPAGE)自然 2M 折叠。
  • 反大页：sandbox-ctl 二进制 strings 里存在 madvise NOHUGEPAGE 调用（对特定 vhost/uffd 区域主动禁 THP）。
  • 回收：idle 沙箱经 balloon inflate 交回内存 → 落账更小 reservation → 供 burst 沙箱复用（多路复用，不硬占 Capacity）。
部署实测：三条宿主机 /proc/meminfo 均为 HugePages_Total=0（无预分配大页），AnonHugePages 非零（THP 生效）。与源码结论完全一致。

3.3 NUMA 亲和：无（结构性跨 NUMA）

  • schema 与代码均无 NUMA 相关字段：不向 Cloud Hypervisor 传 --memory-zone host_numa_node=（mbind 绑内存节点）、不传 --numa（guest SRAT/SLIT 模拟）。
  • guest 视角单 NUMA（此前采集 dmesg 报 No NUMA configuration found + Faking a node），不感知宿主机拓扑。
  • vCPU 不绑核 + 内存不绑节点 ⇒ 沙箱的 vCPU 与内存物理位置不可控，跨 NUMA 访问是结构性必然。
部署实测：x86 宿主机 cpuset.cpus.effective=8-511 横跨 node0/node1，cpuset.mems.effective=0-1 不限制任何节点；ARM 宿主机 8-143/8-151 配 0-3 全节点。单个 runner 的 memory.numa_stat = anon N0=118MB N1=0 只是分配时自然落位，非强制亲和。

3.4 管理面 / 数据面 CPU 隔离：池级 cpuset，非独占 partition

kuasar-sandbox 的 cgroup 层级（cgroup v2）按角色分区，但只做「池级 cpuset 圈地」，不做「per-sandbox 独占绑核」：

/sys/fs/cgroup/sandbox.slice/
├── cpuset.cpus = 8-511          # 整个沙箱池：跳过 0-7 这 8 个核给宿主系统/管理面
├── cpuset.mems = 0-1            # 不限制 NUMA 节点
├── sandbox-platform.slice/      # conductor / proxy（管理面 + 数据面）→ 也在这个池内
├── sandbox-runner.slice/        # 每个业务沙箱一个 sandbox-runner@sr-*.service（vCPU+业务）
└── sandbox-builder.slice/       # 模板构建（build）池
  • 有：把 0-7 这 8 个核从「沙箱视角」挖掉，留给宿主 OS / nacre-agent / 云监控 agent。
  • 没有：cpuset.cpus.exclusive / cpuset.cpus.partition(isolated) / isolcpus —— 系统进程理论上仍可被调度到 8-511，与沙箱争抢。管理面(conductor)与数据面(proxy)也不独占独立核。
  • 节点级 nacre-agent 用 --sandbox-limited-milli-cpus/--sandbox-limited-memory-mib 控制总量配额（如 512 核机只给沙箱 90%），不是空间隔离。

3.5 节点准入：Reservation Controller（node-ctl）

节点级把内存当作「可回收、可复用」的共享池，配一套水位分区 + 令牌桶：

机制作用
Physical / HostReserved / PostHostBudget物理内存 → 扣除宿主保留 → 可分配预算
AllocatablePool再扣 operational_margin_factor(10%) 后的可分配池
Zone：green→yellow→red→critical按 Reserved 占池比例分水位（low 70% / high 85% / critical = P−emergency 5%）
StartupPool / 准入令牌桶限制并发创建/恢复的聚合内存；admission rate/burst 控创建洪峰
Grant（RequestBudget）/ Cooldown运行时增长先记账后放行；未批满则按 cooldown 重试

设计目标：「高密度 = 提高有用利用率，且不把 OOM 当作调度手段」。Red/Critical 区拒绝新创建、保留恢复与搬出，用 balloon + 暂停（pause → snapshot）把 long-idle 沙箱按需压到持久态。

四、华为部署实测对照（三条 BMS 宿主机）

kuasar-sandbox 的华为商用部署形态即实测的 nacre-agent / sandbox-ctl / node-ctl / connector-ctl（--sandbox-runtime-type=E2B、--agent-type=BMS）。宿主机实测与源码结论逐条互证：

  • 绑核 = 否：单 runner cpuset.cpus 为空（继承池级 8-511），无 exclusive partition。
  • 大页 = 否：HugePages_Total=0，仅 THP；字符串含 madvise NOHUGEPAGE。
  • NUMA = 否：cpuset.mems 覆盖全节点，vCPU 漂移，跨 NUMA 必然。
  • 隔离 = 池级：仅 8 核留宿主（0-7），数据面/管理面不独占；观察期 guest 内 %steal=0 未现明显抢占。

五、友商策略对比

下表把「能真绑核 + 真 NUMA 透传」的能力边界铺开（来源见附注）。核心规律：能做的只有 Kata(QEMU 路径) 和 Cloud Hypervisor 原生；Firecracker/gVisor 刻意把绑核/NUMA 交还宿主编排层。

对象① CPU 绑核② 内存页型③ NUMA 亲和④ 管理面/数据面隔离
kuasar-sandbox否（cpu.weight）小页+THP（无大页）否池级 cpuset（8 核留宿主）
Kata 3.x（QEMU/Go runtime）可选 enable_vcpus_pinning三档 小页/THP/静态大页可选 enable_numa + policy=bind依赖 K8s CPU Manager static
Kata 3.x（CLH/Dragonball）未接线/需查证小页/THPruntime-rs 尚不支持同上
Firecracker（AWS 生产）本体否；宿主 cpuset.cpus+partition isolated匿名/memfd，无大页无 balloon宿主 cpuset.mems 钉节点外部 cgroup partition isolated
gVisor（runsc）无 vCPU/绑核单 memfd + 宿主 THP无Core Scheduling（SMT 隔离）
Cloud Hypervisor（VMM 原生）可选 --cpus affinity小页+thp=on；可选 hugepages/prefault/KSM是 host_numa_node+--numa无 partition（由宿主承担）
E2B（Firecracker 系）未公开Firecracker memfd，无 balloon未公开未公开

要点：① Cloud Hypervisor 明明内置 affinity/hugepages/host_numa_node/numa，kuasar-sandbox 却一个都没启用——这是「高密度软隔离」的设计取向，而非能力缺失。② Kata QEMU 路径是唯一「绑核+NUMA+大页」开箱即用的容器运行时，但依赖 K8s Guaranteed pod + static policy。③ Firecracker 走的「外部 cgroup partition isolated」正是 kuasar-sandbox 目前没有做的那一步。

六、结论与洞察

不绑核cpu.weight 权重
无静态大页小页 + THP
无 NUMA 亲和结构性跨 NUMA
池级 cpuset8 核留宿主
内存多路复用balloon + reservation
  1. 定位是「高密度软隔离」，不是「性能确定性」。 kuasar-sandbox 的 CPU 只有「vCPU 数」和「cpu.weight 相对权重」两个旋钮，把「绑核/NUMA/大页」全部让渡给宿主机 CFS + THP，换取更高的并发密度（官方 851s→380s x86、802s→333s ARM 的固定并发对照即这种设计的收益）。
  2. 资源模型的创新点在「内存侧」而非「CPU 侧」。 它比 Firecracker（无 balloon、不回收）激进：用 virtio-balloon + NodeReservation 账本 + memory.high 节流，把 idle 内存跨沙箱复用，且刻意「不用 OOM 当调度器」。
  3. CPU 空间隔离是明确的留白。 唯一隔离是「池级 cpuset 把 0-7 留宿主」，但没有 exclusive cpu partition / isolcpus，多沙箱 vCPU 必然互相重叠、与系统进程争抢 8-511。若未来要确定性延迟，这就是第一个要补的点（参考 Firecracker 的 cgroup partition isolated 实践）。
  4. 与火山/华为对照现象的呼应。 此前命令耗时对照里「琐碎小命令正负互现、离群点抖动大」，与「vCPU 不绑核 + 跨 NUMA」的软隔离模型自洽——非独占 CPU + 跨 NUMA 会放大单次短命令的波动。
  5. 若要升级： 能力都已存在于 Cloud Hypervisor 层，只需 sandboxer 暴露出 --cpus affinity（绑核）、--memory hugepages（大页）、--memory-zone host_numa_node+--numa（NUMA），再加编排层的 exclusive cpuset 分区即可覆盖当前全部缺口。
