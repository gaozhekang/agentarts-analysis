五页 PPT 生成任务 · 火山 vs 华为（第二次 / r2）镜像对照与差异分析

两个 2026-11-05 采集包逐项对照：火山 A/B 与 华为 r2 A/B。结论一句话——业务镜像、Tape、skill 完全相同，差异只落在 Runner 二进制 与 沙箱 guest 内核 上，不能把差异全归因于云厂商。

核心定调：两包 observer 镜像 digest 同为 sha256:6b37dc226033…，observer sha、Tape A/B、模板规格（4 vCPU / 8192 MiB）、Python（3.12.15）、ECS guest 内核全部一致。命令账本（A 32 条 / B 39 条）及其成功/失败模式逐条一致，CPU/内存/网络画像几乎一致。唯一真正的差异是：① Runner 二进制不同（火山用了独立修复版），② 沙箱 guest 内核不同，③ 由此带出的 B 域采集窗口/perf 体积与磁盘 I/O 模式差异。

5.2 差异解读

  • TOP 10 全部是「火山更快」（整体 45/71 更快、净快 ~3443 ms）；华为只在琐碎命令（ls/cp/mkdir/echo，单条 <100ms）偶有领先，累计只省 449 ms，不足以反转。
  • 差异最大的是「fork/exec 密集」与「文件系统遍历」命令：find / 全盘扫描合计火山快 33.5%（A·3 快 56% 、B·3 快 41%），版本检查子shell合计快 39.1%（A·6 快 59%：命令里 4 个 $(…) 各是一次 fork+exec）。说明火山沙箱的进程创建/exec 与目录元数据遍历开销明显更低。
  • CPU 密集命令火山也更稳：soffice 渲染合计快 15.5%（A·27 快 28% 、B·35 快 9%），node slides.js 快 13%～14%（A·28/A·29），python3 finalize_deck.py 快 21%～24%（A·17/A·18）。幅度不如 find / 版本检查夸张，但方向一致。
  • 根因落在「沙箱 guest 内核 + 底层实例硬件」：同一镜像、同一 Tape 只保证 workload 一致，不保证底层 vCPU 型号 / 磁盘 / 内核一致。火山沙箱（6.6.95.bck.4-rc3-amd64）与本轮华为 HCE（6.6.0-72.0.0.76…hce3）在 fork/exec 路径、页缓存与调度上确有可观察差异。要拆到「内核 vs CPU 型号 vs 磁盘」需补 sysbench / perf stat（IPC、频率、syscall 耗时）这类微基准。
  • 不改变既有结论：这份「同镜像跨云」的 ~10%~25% 量级墙钟差异，恰好说明把差异全归因云厂商不对、全归因 Runner 也不完整 —— 真正的变量是三元的：Runner + 沙箱内核 + 底层实例；其中命令耗时差异主要由后两者驱动（Runner 只影响采集器存放路径与 ENOSPC 停止，不影响业务命令执行时长）。

六、结论

  1. 核心画像一致：两包业务镜像、Tape、skill、模板规格完全相同，命令账本（数量/成败/perf 关联）逐条一致，CPU/内存/网络画像误差 <5%。
  2. 真实差异只有两处根因：① Runner 二进制（火山独立修复版 vs 华为前身），② 沙箱 guest 内核（6.6.95.bck.4-rc3-amd64 vs HCE 6.6.0-72.0.0.76…hce3）。
  3. 次生差异：B 域采集窗口（222s vs 147s）→ perf 体积（87 vs 58 MB）→ 采样量（12345 vs 8670）→ 归因占比（94.5% vs 89.7%）；以及 B 域磁盘读写方向相反。
  4. 归因要谨慎：上述次生差异同时受「Runner 差异」与「沙箱内核差异」影响，不能把 B 域窗口/采样差异直接说成云厂商性能差异；火山 B 跑得更长是其 Runner 停止/确认修复的预期效果之一。
  5. 火焰图/CPU 归因结论不变：吃 CPU 的是 harness/Agent 运行时（ecs 与 B 域），worker 只跑短命 tool 命令，两包定性一致。
