华为 Gray 沙箱 · Guest 内核调参对比实验汇总

生成日期：2026-11-12  ·  实验执行：2026-11-10 ~ 11-12  ·  架构：x86 (10.30.33.139) + arm (10.30.33.67)  ·  Guest 内核：6.6.0（EEVDF，Cloud Hypervisor 微虚拟机）

一、一句话结论

对华为 Gray 沙箱 guest 内核做了 7 组调参实验。前 6 组用自计时 4 场景 workload（fib + 内存拷贝 + 文件读写 + fork 64 进程），结论：5 组「纯调度/回收/定时器」参数对负载毫无影响（base_slice_ns、MGLRU、WAKEUP_PREEMPTION、NEXT_BUDDY、HZ），因为负载是「子进程只算不睡、CPU 全程打满」的纯计算场景，这些参数作用的路径（唤醒抢占、回收压力、时间片切分、定时 tick）根本不被触发；唯一有显著收益的是 mTHP（多尺寸透明大页），把 memory_s 从 0.239s 压到 0.072s（3.3× 加速）。

第 7 组针对「EEVDF / mitigations / HZ 对 harness（进程编排/IO 密集）vs worker（CPU 密集）有无提升」的问题，把 workload 扩到 6 场景（新增 syscall 压测 + ctx_switch 上下文切换，内存 256→2048MB 调到秒级），对比 mitigations=off 与基线。结论：x86 上 syscall_s 2.69× 加速（1.804→0.670s）、ctx_s 降 14%（这是 retpoline/IBPB/RSB-filling 的真实开销）；arm 与纯计算项（fib/fork）完全无差 —— 即 mitigations=off 只对 x86 的 syscall/上下文切换密集型（harness 类）负载有用，EEVDF/HZ 两类场景都无感。

fork 三组 28.549 / 28.593 / 28.504，极差仅 0.089s（0.312%），噪声内。fork/fib 稳定 7.93~7.99×。arm 侧（1ms/2.25ms/4.5ms）同样无影响。结论：时间片粒度不改变满载纯计算的吞吐（满载时总吞吐 = 墙钟 × vCPU，与时间片长短无关）。

4.6 mTHP（多尺寸透明大页）—— 唯一有显著收益的项

内核为 HCE 6.6，backport 了 6.8 的 mTHP，完整 hugepages-8kB ~ 2048kB 多尺寸 sysfs。开启方式：

echo always > /sys/kernel/mm/transparent_hugepage/enabled          # 顶层（2MB PMD）
echo always > /sys/kernel/mm/transparent_hugepage/hugepages-64kB/enabled
echo always > /sys/kernel/mm/transparent_hugepage/hugepages-32kB/enabled
# ... 16/128/256/512/1024/2048 kB 同理（默认全 never，2MB 为 inherit）

4.6.1 确认 workload 真的用到了 mTHP（计数器增量，单次运行）

计数器x86 增量arm 增量说明
thp_fault_alloc（2MB PMD）+259 页 ≈ 518MB+261 页 ≈ 522MB≈ MEM_MB×2 = 512MB 全覆盖

这正是「多尺寸 THP 同时参与」的证据：bytearray(256MB)×2 的匿名分配，大头 2MB、边角 64kB。用 /proc/vmstat 的累计计数（thp_fault_alloc、nr_anon_transparent_hugepages）跑前后取差值即可证明。

只有 memory 阶段变快，CPU 阶段（fib/fork）几乎不动 —— 提升纯粹来自内存分配路径。为什么是 3.3× 而非通常的 TLB 10~30%？因为这个沙箱内存是 UFFD 懒加载 + diff-cow，单次缺页很贵：bytearray(256MB) 首次写入，THP 关时每块 buffer 触发 65536 次 4KB 缺页（×2 块 = 13 万次），开 THP 后骤降到 128 次 2MB 缺页（缺页数减少 512 倍）+ TLB 压力 65536→128 条，两项叠加撑出 3.3×。

arm 侧说明：arm 的 mTHP 使用已经计数器确认（+261/+60 页），但那一轮 arm 基准本身噪声很大（memory_s 0.086~0.215 乱跳、fileio_s 也从历史 ~0.043 翻倍到 ~0.10、还冒出 fork=56.8 离群）——是 67 宿主机当时变忙导致，不是 mTHP 的问题。arm 顶层默认即 always，历史 memory_s ~0.078 已经是 THP 加速后的值。要干净的 arm 数字需等宿主机空闲单独测。

4.7 CPU mitigations（mitigations=off vs 基线）—— 只对 x86 的 syscall/上下文切换型负载有效

为回答「EEVDF / mitigations / HZ 对 harness（进程编排/IO 密集）vs worker（CPU 密集）有无提升」，把 workload 扩到 6 场景：新增 syscall（os.getppid() × 1e7 —— 非 vDSO 缓存、每次真进内核）与 ctx_switch（双管道 fork 乒乓 × 2e5 轮，每轮 2 次切换），并把 MEM_MB 256→2048 调到秒级（x86 稳态 ~1.2s）。

关闭 mitigations 用方式 D：直接改内核源码默认值 kernel/cpu.c:3179 的 cpu_mitigations __ro_after_init = CPU_MITIGATIONS_OFF（等效把 mitigations=off 写死，无需改 cmdline），重编内核后走「重新 build → 切配置 → 重建」打快照。内核 digest：off x86 1b1bba86… / arm f4d580a6…；基线（on）x86 bffa66b8… / arm edf79a5d…。沙箱内校验：off 后 x86 spectre_v2 → Vulnerable; IBPB: disabled; STIBP: disabled、spec_store_bypass → Vulnerable、spectre_v1 → Vulnerable；arm spec_store_bypass → Vulnerable（arm 的 spectre_v2 硬件 Not affected，spectre_v1 是编译期写死的 __user sanitization、关不掉）。

核心结果：x86 上 syscall_s 从 1.804s 降到 0.670s（2.69× 加速，单次 syscall 180.4ns→67.0ns、每次省 113.4ns），ctx_s 降 14%（6.88→5.92µs/切换）。这正是 AMD Milan 上 retpoline（lfence 变体）+ swapgs/spectre_v1 屏障 + IBPB-on-ctx-switch + RSB-filling 的真实开销，在 syscall/上下文切换密集时被放大。arm 则完全无差（syscall −0.0%，两组 std 均 <0.003）—— 因为 arm spectre_v2 硬件 Not affected，本来就没有 retpoline 可关。
打 * 的三项不是 mitigations 效果：① memory_s 是「2GiB alloc + copy」纯内存带宽，与 mitigations 无关 —— 差异来自两组沙箱实例不同时刻的宿主/UFFD 懒加载状态（arm ON 组 std 高达 0.244、min 0.70 / max 1.57 乱跳，方向还与 x86 相反，正说明与 mitigations 无关）；② arm ctx_s 的 −21.2% 同样可疑（ON 组 std 0.564、min 2.87 / max 4.47，是 67 宿主机瞬时变忙，不是 mitigations）。可信信号只有 x86 的 syscall −62.9% 与 ctx −14.0%（两组 std 都很小、干净），以及 arm 的「syscall 完全无差」。

正面回答「mitigations 对 harness/worker 有没有提升」：worker（纯计算 fib/fork）无感（+0.9% / +1.1%，噪声内）；harness（syscall/上下文切换密集的进程编排）在 x86 上有实打实收益（syscall 2.69×、ctx 14%），arm 无收益。结合前 6 组，四个 knob 里唯一对 harness 有用的是 x86 的 mitigations=off，EEVDF 与 HZ 对两类场景都无感。

五、共性结论：为什么「调度/回收/定时器」参数都无感，而 mTHP 例外

参数作用的机制本负载是否触发
base_slice_nsEEVDF 时间片切分周期否 —— CPU 满载，吞吐=墙钟×vCPU，与时间片无关
WAKEUP_PREEMPTION睡眠任务被唤醒时能否抢占否 —— fork 子进程只算不睡，无「睡眠→唤醒」
NEXT_BUDDY唤醒后优先被调度否 —— 同样依赖唤醒事件
MGLRU内存压力下的回收老化否 —— 512MB ≪ 8GiB，不触发回收
HZ定时 tick 频率（jiffies 粒度）基本否 —— 纯计算进程几乎不被打断，tick 开销约 0.02% 量级
mTHP匿名内存分配粒度（缺页次数/TLB 压力）是 —— 内存阶段每一步都在分配/触页，直接受益
mitigations=offretpoline/IBPB/RSB-filling 的每次 syscall、每次切换开销x86 是（syscall/切换密集时）；arm 否（硬件 Not affected）

一句话：前 6 组这份「CPU 打满、子进程不睡眠、内存远小于物理上限」的纯计算负载，让所有针对「调度切换 / 唤醒 / 回收 / 定时」的调优点统一失效，唯有直接作用于「内存分配粒度」的 mTHP 生效。要让调度类参数体现差异，必须换成有睡眠/唤醒、有 I/O 等待、或 CPU 未满载的负载（如子进程里加 usleep/sched_yield、短活 fork/exec churn、或内存压力场景）。但 mitigations 是另一类参数：第 7 组证明，只要负载变成 syscall/上下文切换密集（即 harness 类的进程编排），x86 上 mitigations=off 立刻显出 2.69× 的 syscall 收益——同一份纯计算负载测不出它，纯粹是因为计算路径不进这些被缓解的代码。

六、附录：内核调参与内核替换的落地方法

6.1 运行时参数（debugfs / sysfs，沙箱内即可改）

# 先挂 debugfs
mount -t debugfs debugfs /sys/kernel/debug

# 调度时间片
echo 2250000 > /sys/kernel/debug/sched/base_slice_ns          # 默认 2250000

# 调度 feature（前缀 NO_ 表示关闭）
echo WAKEUP_PREEMPTION > /sys/kernel/debug/sched/features       # 开启唤醒抢占
echo NO_NEXT_BUDDY     > /sys/kernel/debug/sched/features       # 关闭 next buddy

# MGLRU（内核 CONFIG_LRU_GEN=y）
echo 0x0007 > /sys/kernel/mm/lru_gen/enabled                    # 开启（生效为 0x0003）

# mTHP
echo always > /sys/kernel/mm/transparent_hugepage/enabled
echo always > /sys/kernel/mm/transparent_hugepage/hugepages-64kB/enabled

注意：这些运行时参数在沙箱重启（快照恢复）后全部回默认，每轮实验前需重设。沙箱生命周期 1 小时。

6.2 编译期参数（HZ / 内核替换）—— 必须重新 build 打快照

# 1) 在节点源码树重编内核（如改 HZ）
cd /home/gzk/kernel
sed -i 's/^CONFIG_HZ_100=y/# CONFIG_HZ_100 is not set/; s/^CONFIG_HZ=100/CONFIG_HZ=250/' .config
# 打开目标 HZ 子项并 make
make -j$(nproc) Image   # arm64 产物 arch/arm64/boot/Image（x86 为 bzImage）

# 2) 覆盖节点内核文件（仅这样不够 —— 见下）

十一、harness 命令耗时实测（mTHP=always + thp_exec_enabled · x86 & arm · 各 5 轮）

同第八章口径：前端 ppt_replay 回放（32 条沙箱命令生成 PPTX，不调真模型），读 performance.summary.commands.sum_ns，每轮全新沙箱。本轮在 HZ=100 内核上重编开启 CONFIG_READ_ONLY_THP_FOR_FS=y（x86 85143e74… / arm 31e957b9…，均为 6.6.0+ 新 build），并注入 mTHP 全尺寸 always + thp_exec_enabled=0x3，对比 HZ=100 基线（第十章）与第八章 mTHP。

  • mTHP：顶层 enabled=always + hugepages-2048kB~16kB 全 echo always（沙箱内回读确认各档 [always]）。
  • thp_exec_enabled：hex 位图，写 0x3。bit0 = FILE_EXEC_THP_ENABLE（exec 映射用 2MB PMD THP，经 try_enable_file_exec_thp / khugepaged 生效，需 CONFIG_READ_ONLY_THP_FOR_FS=y）；bit1 = FILE_EXEC_MTHP_ENABLE（exec 映射用 mTHP 小 folio，消费点 file_exec_can_enable_mthp）。

关键源码事实：bit1 的最终生效门是 arch_wants_exec_folio_order，只在 arm64 定义（arch/arm64/.../pgtable.h:1206 → ilog2(64K>>12)=order 4，即 exec 用 64kB folio），x86 未定义故 bit1 在 x86 上是 no-op；bit0 在 CONFIG_READ_ONLY_THP_FOR_FS=y 后两架构均生效。即：x86 仅 2MB exec THP 起作用；arm 有 2MB exec THP + 64kB exec mTHP 双路径。该 knob 只接受十六进制，写 always 会 EINVAL（实测 rc=1）。

流程（每轮）：建沙箱 → 开终端注入 mTHP + thp_exec → 回读校验 → 关终端 → 跑 ppt_replay → 读耗时 → 删沙箱，两架构各 5 轮。
