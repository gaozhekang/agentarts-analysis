一、三个被测命令

ppt_replay harness 回放的 32 条命令中，按累计耗时排序的 Top3 全部是 LibreOffice 的 soffice 相关命令。我们对这三条命令抓了完整 strace：

编号命令角色一句话定位
#6soffice --version环境探测冷启动：首次加载动态库 / 字体 / fontconfig
#27soffice --headless --convert-to pdf … final.pptx核心转换（第 1 次）PPTX → PDF 完整转换，耗时最大，分析重点
#32soffice --headless --convert-to pdf … final.pptx核心转换（第 2 次）预热后的重复转换，与 #27 对照

二、整体 syscall 分布（strace -c）

三条命令的 strace -c 汇总里，时间高度集中在三个 syscall：wait4、futex、accept。以核心转换 #27 为例：

syscallarm #27x86 #27含义
wait4等待42.8%（2.99s）42.1%（1.66s）父进程等 soffice.bin 子进程退出
futex等待36.2%（2.53s）34.7%（1.37s）线程在条件变量上等 soffice.bin 完成
accept等待19.7%（1.38s）18.0%（0.71s）PipeIPC 线程等 SingleOfficeIPC 套接字回连
pread64磁盘0.27%（0.019s）0.52%（0.021s）磁盘顺序读，可忽略
其余 ×20+<1%<2%openat / mmap / munmap / execve 等，瞬态
⚠️ strace -c 的「时间合计」会虚高，不能直接读成「总耗时」。 strace -f 跟随所有线程/进程，把互相重叠的等待时间做跨线程累加： arm #27 三大 wait 之和 2.99+2.53+1.38 = 6.90s，而 soffice.bin 实际墙钟只有 2.02s（3.4×）； x86 #27 三项之和 3.75s，实际墙钟 1.46s（2.6×）。 这正是本文要澄清的核心：三者的时间不是串行叠加，而是同一件事的三种重叠等待。

三、三大耗时 syscall 各自「在等什么」

3.1 进程树：一次 soffice 转换的真实调用链

# arm #27（x86 完全同构，仅 pid 不同）
533  /bin/sh -c "… soffice --convert-to pdf … | tail; pdftotext …; grep …; python3 …"
└─ 534  /usr/bin/soffice                # shell 包装脚本
      └─(exec)─▶ oosplash              # LibreOffice 启动器（仍 534）
           ├─ 线程 549 osl_executeProc ──fork──▶ 550 soffice.bin  # ★ 真正的转换进程
           │        ├─ 线程 551/556 configmgrWriter、554/557 Unzipping、555/562 Parser …
           │        └─ 线程 552 PipeIPC  # ★ 阻塞在 accept 的监听线程
           └─ 535 tail -2
# 转换完成后：sh 继续跑 pdftotext(597) → grep → python3(600)

证据（arm）：550 04:55:04.268542 execve("/usr/lib/libreoffice/program/soffice.bin", …)； x86：545 04:54:35.240305 execve(…soffice.bin…)。两侧 soffice.bin 路径、参数完全一致。

3.2 wait4（~41%）—— 等的是 soffice.bin 转换子进程退出

父进程（oosplash 的 osl_executeProc 线程，以及最外层 /bin/sh）调用 wait4 阻塞， 等真正干活的 soffice.bin 结束。递归看，最长的 wait4 = 等 soffice.bin（arm 约 2.07s / x86 约 1.50s）， 外层的 wait4 与它嵌套重叠；其余 wait4 是 dirname/basename/ls/sed/grep/pdftotext/python3 这些瞬启瞬退的小工具。

3.3 futex（~35%）—— 等的是条件变量上的「soffice.bin 完成」通告

oosplash 主线程在 pthread 条件变量上做 futex(FUTEX_WAIT)，等 soffice.bin 完成退出； 决定性的一条等待 arm 约 2.02s / x86 约 1.45s。当 osl_executeProc 线程在 wait4 返回后、 用一条 futex(FUTEX_WAKE) 唤醒它，链条闭合：futex 和 wait4 是同一件事在主/子线程两侧的镜像。

3.4 accept（~19%）—— 等的是 SingleOfficeIPC 套接字的 shutdown 握手

soffice.bin 的 PipeIPC 线程阻塞在 LibreOffice 的单实例 IPC UNIX 套接字上：

# arm：
550 bind(11, {AF_UNIX, "/tmp/OSL_PIPE_0_SingleOfficeIPC_9b4c95dea5e491cdcd7b5b42ab77eb"}) = 0   # 04:55:04.4219
552 accept(11, NULL, NULL <unfinished …>                                                  # 04:55:04.4227 ★ 阻塞 1.14s
550 connect(7, {AF_UNIX, "…SingleOfficeIPC_…"}) = 0                                        # 04:55:06.2711 转换完成后回连
550 unlink("…SingleOfficeIPC_…")                                                          # 握手后删除套接字

即：soffice.bin 转换结束后（unlink .lock 之后），主线程才 connect 回自己的监听套接字做 shutdown 握手， PipeIPC 线程才从 accept 醒来。全程没有任何外部客户端连入 —— 是空闲监听线程的自阻塞。 注意 arm / x86 的套接字路径完全相同（同一 UID 下由固定 hash 派生，与机器无关）。

四、核心结论：soffice 转换本质是 CPU-bound

wait4 / futex / accept 不是三个独立瓶颈，而是「同一次 soffice.bin 转换」的三种等待形式，时间高度重叠。 真正的耗时在 soffice.bin 的 CPU 计算上——更精确地说，内核态 si_stime 是用户态 si_utime 的 ~1.6 倍 （arm 0.99s vs 0.60s / x86 0.58s vs 0.38s），其中大头是缺页异常（page fault），见 7.5 节。

最强证据：soffice.bin 退出时内核记账的 CPU 时间（SIGCHLD 的 si_utime/si_stime）：

进程墙钟 wall用户态 utime内核态 stimeCPU 合计CPU 占比
arm soffice.bin(pid 550)2.02s0.60s0.99s1.59s~79%
x86 soffice.bin(pid 545)1.46s0.38s0.58s0.96s~66%

证据：arm 行 14903 SIGCHLD …, si_utime=60/*0.60s*/, si_stime=99/*0.99s*/； x86 行 17179 si_utime=38/*0.38s*/, si_stime=58/*0.58s*/。墙钟 = execve → 退出信号的时间差。

❌ 修正之前的错误结论：早前一度判为「soffice 慢既非 CPU 也非磁盘 IO（进程/线程同步 ~77% + UNO IPC ~18%）」—— 这是被 strace -c -f 的跨线程重叠累加误导。实测 soffice.bin 的 CPU 时间占墙钟 66%~79%， 用户态 PPTX 渲染 + 内核态缺页/系统调用是主体，磁盘 IO <1%、无任何网络。

五、#6 冷启动的独特性

soffice --version（#6）分布明显不同：wait4 占 ~75%（arm 74.9% / x86 72.5%）、futex ~22%， 且总耗时很短（arm 0.85s / x86 0.27s）。这里的 wait4 是在等 soffice.bin 做启动自举—— 加载动态库（一次运行 5600+ 次 pread64/mmap）、字体/fontconfig/config，打印版本号后立即退出。没有 convert 的 CPU 计算段。

七、soffice.bin 本体 per-pid 剥离画像（直接证据）

前面的 CPU 占比（66~79%）来自 SIGCHLD 的 si_utime/si_stime 内核记账，属间接证据， 且墙钟里混入了 oosplash / /bin/sh / tail 等外壳进程。 2026-11-19 用 strace -ff（每进程/线程独立追踪文件）重新抓取，按 execve 命中 soffice.bin 把转换本体的 syscall 序列完整剥离出来（x86/arm 各 3 份： #6 探测、#27/#32 两次转换），得到直视本体 CPU/IO 构成的直接证据。

剥离方法：strace -ff -o trace 会为每个 task 写 trace.PID； 从每个 trace.PID 里筛出 execve(.../soffice.bin...) 的那份，即为本体。 这一层丢掉了外壳的 wait4/futex/accept 噪音——剥离后三者全部消失，进一步印证它们是外壳层等待、不属于本体计算。

⚠️ 这里的「其余（墙钟 − syscall）」不是纯用户态，切勿读成「用户态 CPU」。 strace -T 只累加系统调用的耗时；而缺页异常（page fault）不是 syscall、strace 不追踪。 它发生在用户态代码访问未加载内存时，被算进了「墙钟 − syscall」这个差值里——但它本质是内核态工作。 真正的用户态/内核态拆分要用内核记账 si_utime/si_stime，见 7.5 节。

转换本体墙钟 1.28~1.44s，strace 可见的 syscall 耗时仅 20~23%；剩下 77~81% 是「用户态指令 + 缺页异常 + 调度等待」的混合， 不能等同于用户态 CPU 时间。

关键修正：本体层面 arm 并不比 x86 慢。 之前第四节 SIGCHLD 记账得出「arm 2.02s vs x86 1.46s 慢 38%」，那个墙钟混入了 oosplash/sh 外壳层。 剥离本体后 arm 1.28~1.34s 与 x86 1.44s 相当、甚至略快（arm syscall 耗时 20% 反而低于 x86 22%）。 说明「arm 慢」主要在外壳层的 fork/exec/等待链路，而非 soffice 渲染本身。此为不同次运行的新样本，方向性差异需更多样本确认，但至少否定了「arm 渲染更慢」的假设。

7.2 时间线三阶段：启动自举 → 渲染 → 写 PDF

以转换本体（相对 execve 起点）的关键事件时间戳，清晰切成三段：

事件（相对 execve）arm #32x86 #32
execve(soffice.bin)0.000s0.000s
首次 open 输入 .pptx+0.512s+0.808s
首次 open 输出 .pdf+1.203s+1.375s
首次 write PDF+1.204s+1.375s
退出1.280s1.438s
阶段arm #32x86 #32在做什么
① 启动自举0.51s（40%）0.81s（56%）加载 234 个 .so + 374 个字体 + fontconfig
② 渲染转换0.69s（54%）0.57s（40%）读 PPTX → 版面/绘图计算 → 建 PDF 结构
③ 写 PDF 收尾0.08s（6%）0.06s（4%）写 192KB PDF + fsync + 退出

启动自举占墙钟 40~56%，与渲染本身同量级——这是 LibreOffice 每次沙箱都要重付的冷启动成本。 有趣的交叉：arm 启动自举更快（0.51s vs 0.81s，文件映射 638 vs 960 更少），但渲染更慢（0.69s vs 0.57s）； x86 相反。两者最终墙钟接近，差异被互相抵消。

374 个字体枚举是启动自举的最大头，印证第四节「线程在等 oosplash 加载字体」的间接观察； 也直接坐实第 3 步结论：模板快照时 init+envd 未加载业务动态库/字体，所以每次转换都要冷加载 234 个 .so + 374 个字体。若想压缩启动段，预热方向是：模板固化前 touch 一遍字体目录 + 跑一次 soffice --version 把 .so/字体页缓存进 host page cache（这会改变「冷启动」口径，需有意为之）。

7.4 线程与 syscall 风格：41 线程并发 + arm/x86 ABI 差异

  • 线程数：本体创建 41 个线程（#6 探测为 0——--version 不起渲染线程池）。x86 用 clone×5 + clone3×36，arm 全用 clone×41；glibc 在 x86 上优先走 clone3，纯 ABI 差异，无性能含义。
  • mmap 差异：x86 文件映射 960 次 vs arm 638 次，arm 匿名映射 267 vs x86 102——arm 侧匿名内存更多（缺页更频繁），对应 7.2 里「arm 渲染段略慢」。
  • syscall 风格：arm 用 *at 封装（faccessat×758 / readlinkat×307），x86 用元调用（access×758 / readlink×307），同一操作、不同 glibc 封装。
  • 写 PDF 落盘：write/pwrite64 写 PDF 合计 196,802 字节（~192KB），arm 另有 fdatasync×12（0.014~0.017s）显式刷盘；x86 无 fsync。量级远小于渲染段，坐实「磁盘 IO 可忽略」。

7.5 缺页异常（page fault）：内核态的真大头，strace 看不到

把 strace 的 syscall 耗时与内核自己的 CPU 记账（第四节 SIGCHLD 的 si_stime）交叉对比， 即可分离出 strace 看不见的缺页异常开销。x86 两组数据墙钟恰好接近（1.46s vs 1.44s），可直接相减：

内核态构成（x86）时间占墙钟占内核态
真·内核态合计 si_stime（SIGCHLD 记账）0.58s40%100%
　└ syscall 耗时（strace -T 可见）0.32s22%~55%
　└ 缺页异常 + 中断/调度（strace 不可见）≈0.26s18%~45%

arm 上这个占比更高：si_stime = 0.99s，而 syscall 仅 ~0.27s，缺页异常等约 0.7s、占内核态 ~70% （注：arm 两组为不同运行、墙钟 2.02s vs 1.34s 差异大，此处是量级参考；x86 为可靠对比）。

page fault 完全归类在内核态（si_stime），与用户态（si_utime）无关。 缺页在内核 do_page_fault → handle_mm_fault 路径里完成（分配物理页、从 page cache 读入、填页表）， 进程这段时间运行在内核态。因此之前 7.1 的「其余 77~81%」里，有相当一部分其实是内核态的缺页处理。

为什么缺页这么多：冷启动要按需加载 234 个 .so + 374 个字体 + 渲染数据结构。 mmap 只建立 VMA 映射（syscall 很快），真正的物理页是在之后首次访问该地址时以缺页方式逐页加载的—— 这正是 7.2 里「启动自举占 40~56%」的时间去向：不是跑 CPU，而是填页表 + 从页缓存读 .so/字体。

佐证：arm 匿名映射 267 次 vs x86 102 次（7.4 节），arm 侧匿名内存更多 → 缺页更频繁 → 对应 arm 内核态占比更高； 这与 arm 匿名映射/缺页路径差异一致。精确的缺页次数/时长可用 perf stat -e page-faults,major-faults,minor-faults 在下一次建沙箱时直接数出。

八、结论 & 可落地要点

  • soffice 转换是「冷启动 + 缺页密集」型 CPU 负载：per-pid 直接测量本体墙钟 1.28~1.44s。真·纯用户态 CPU（si_utime）仅 ~26~30%，内核态（si_stime）~40%——其中 page fault 约占内核态一半（x86 ~45%、arm ~70%），比 syscall 本身更贵。不在磁盘 IO（<1%）也不在网络（0）。
  • wait4/futex/accept 是「等它算完」的三种外壳等待，非独立瓶颈：三者时间重叠，被 strace -c -f 跨线程累加放大（arm 三大项 6.90s vs 实际 2.02s）。strace -ff 剥离本体后三者全部消失，坐实是外壳层等待。读 strace 汇总务必警惕这一点。
  • 调优方向：想再压这段耗时，应优先攻冷启动缺页（模板固化前预热 .so/字体到 host page cache，消除 234 个 .so + 374 字体的逐页缺页加载），其次才是 CPU 渲染（CPU 主频、LibreOffice 渲染参数、--convert-to 的 filter），而非磁盘或 NUMA（NUMA 绑核对此负载仅 ~2–3% 收益，见 HostOS 报告第十四节）。启动自举占墙钟 40~56%，是比渲染更易攻的成本项。
  • 本体层面 arm 并不比 x86 慢：剥离外壳后 arm 本体 1.28~1.34s vs x86 1.44s，相当甚至略快。先前「arm 慢 38%（2.02s vs 1.46s）」的差值来自 oosplash/sh 外壳层的 fork/exec/等待链路，而非 soffice 渲染本体。（此为不同次运行的新样本，方向需更多样本确认，但至少否定「arm 渲染更慢」。）
  • HZ 视角印证（HostOS 报告第十五节）：宿主机 tick 频率（100/250/1000）对此 CPU/缺页密集负载几乎无影响（极差 <0.35%），与本结论自洽。
