三、workload 是什么（四场景）

/opt/aries/workload.py，自计时、从环境变量读参数、末尾打印单行 JSON。四个场景：

场景函数什么操作指标
斐波那契bench_fib递归 fib(FIB_N) 重复 FIB_ITERS 次，纯 CPUfib_s
内存拷贝bench_memory分配 MEM_MB MiB ×2 块，整块拷贝 MEM_COPIES 次memory_s
文件读写bench_fileio写 FILE_MB MiB 临时文件再读回，FILE_ITERS 轮fileio_s
fork 多进程bench_forkfork FORK_PROCS（默认 64）个子进程，每个做 fib(FIB_N)×(FIB_ITERS//2)（CPU 量减半），父进程 waitpid 全部回收fork_s

fork 场景语义：测多进程 fork+waitpid 开销与并发 CPU 调度扩展。父进程从 fork 第一个子进程前计时，到全部子进程回收为止。当前配置 FORK_PROCS=64、每个子进程 fib 迭代减半（FIB_ITERS//2），总 CPU 量 = 64×10 = 640 次 fib 迭代 = 32× 主 fib 场景（20 次），分摊到 4 vCPU → fork_s ≈ 8× fib_s。

{"workload": {"fib_s": 3.567, "memory_s": 0.240, "fileio_s": 0.041,
              "fork_s": 28.338, "total_s": 32.185, "process_s": 32.185, "loops": 1}}
# total_s = fib_s + memory_s + fileio_s + fork_s

六、沙箱是怎么被“拉起”的

关键机制结论（实测确认）：华为 Gray 沙箱是 Cloud Hypervisor 微虚拟机。沙箱 PID 1 是平台注入的 /sbin/init，它启动平台注入的 /opt/sandbox-runtime/bin/envd -port 49983。镜像 ENTRYPOINT 被平台完全忽略；常规 create 走 --restore 快照恢复，内核已包含在快照里，不是冷启动。

业务进程有两条执行通道，最终都到达沙箱内同一个 runtime：

  • 控制面/网关侧：envd 的 /process.Process/Start（sandbox_run.py 与 ARIES harness 的同一机制，走 Gateway HTTP）。
  • 宿主侧：sandbox-ctl exec（走本地控制套接字，是本文档第八节的手动入口）。

6.1 快照恢复 vs 冷启动（决定内核能否替换）

# 常规 create（快照恢复，内核在快照里）：
sandbox-ctl run --sandbox-id <uuid> --config <host.yaml> --restore file://<hash>.snapshot …

# 冷启动（build 阶段）读 boot.kernel = /etc/conductor/conductor.yaml 的 sandbox.boot.kernel

所以：改 /opt/sandbox/guest-runtime/vmlinux/vmlinux-26.9.0.1.B006 文件本身不影响已打好的快照；要换内核，必须让新快照在冷启动（build）阶段用新内核。

7.1 关键解读

  • fork_s ≈ 8× fib_s（x86 28.338/3.567=7.94x；arm 55.047/6.890=7.99x）：64 进程 × 10 迭代 = 640 次 fib = 32× 主 fib 场景的 CPU 量，4 vCPU 分摊 → 正好 8× 墙钟。扩展完全线性、fork/waitpid 与 64 进程调度的额外开销可忽略。
  • fork 的 arm/x86 倍率 = 1.94x ≈ fib 的 1.93x：多进程并发扩展是架构无关的，arm 相对 x86 的差距（~1.9x）与单线程 CPU 一致，没有因 64 进程调度引入额外差距。
  • memory 项 arm 反而更快（0.72x）：自定义内核下 arm 内存拷贝稳定在 0.16–0.20s，低于 x86 的 0.24s。
warmup 提醒：快照恢复后首次全参数运行会触发 UFFD 懒加载，memory_s 异常偏高（实测 arm 首轮 ~6.7s、x86 首轮 ~0.56s），随后稳定到上表数值。正式对比建议先跑一次预热、再取 10 组。

8.1 落库路径与修复过程

  1. 在 67 上编译内核：源码树 /home/gzk/kernel，产物 arch/arm64/boot/Image（ARM64 boot Image, 4K pages）。
  2. 用 Image 覆盖平台内核文件 /opt/sandbox/guest-runtime/vmlinux/vmlinux-26.9.0.1.B006。
  3. 第一次 build 失败：内核引导到 init 后，sandbox-init 经 vsock 握手主机超时 → kernel panic。
  4. 根因：CONFIG_VIRTIO_VSOCKETS=m（模块）未内建，EROFS 只读 rootfs 不加载模块 → /dev/vsock 不存在。
  5. 修复：CONFIG_VIRTIO_VSOCKETS=m → y，重新编译，覆盖文件，再次 build 成功。
# 67 上执行
cd /home/gzk/kernel
sed -i 's/^CONFIG_VIRTIO_VSOCKETS=m$/CONFIG_VIRTIO_VSOCKETS=y/' .config
make -j$(nproc) Image
cp arch/arm64/boot/Image /opt/sandbox/guest-runtime/vmlinux/vmlinux-26.9.0.1.B006
